## Product content and Google readiness

- The canonical lifecycle queue is `Digitalogic_Product_Content_Queue`; see `ops/product-content/README.md`. Keep its bootstrap, publication/stock hooks and periodic authoritative sweep intact when changing imports, synchronization or deployment.
- Use the queue's claim, expected snapshot, publish and finish contract for missing-description repairs. Skip a product with another unexpired content claim. Preserve existing nonempty guides and all commercial and identity fields.
- Verify both saved descriptions and the public page before completing content work. Use primary manufacturer evidence, retain unknown board details privately and apply the internal Persian electronics glossary. Do not place store identifiers in either description.
- Sitemap membership and HTTP 200 do not prove Google indexing. Record Google's actual inspection verdict; when new copy was published, retain follow-up until the last crawl is at least as recent as that publication.

## Authentication interface

- Keep username, email, and mobile on one visible sign-in field in the branded card. Digits can keep separate provider inputs internally. Show one Remember me checkbox on the first identity step and preserve the choice through verification. The first complete OTP can submit automatically once per form. Require an explicit submit on retry.
- Keep the placeholder and accessible name in sync with the identity mode. Show «شماره تلفن» when the user enters a phone number. An empty passwordless contact field asks for email or phone. Restore the general prompt on return to an empty sign-in field.
- Keep sign-in, signup, and password recovery in the same card. A new mobile identity must flow into native Digits signup and OTP confirmation without an extra “Not a member yet?” prompt. Show the optional new-password dialog only after successful verification establishes a session. Skipping the dialog must resume the original destination.
- Put account actions beside the form they affect. Keep the passkey action under other sign-in methods. Use one divider style for “Or” and “Or continue with.” Align field icons to the input direction, including LTR phone, email, and password fields on Persian pages.
- Verify the rendered Persian mobile flow as well as the default login URL. Cover direct signup and recovery links, in-card navigation, the unregistered mobile handoff, OTP verification, and return navigation. Distinguish simulated provider responses from real SMS or a completed sign-in when reporting verification.
- Type a phone and an email in the rendered card before shipping. The field icon must follow the identity mode, and the text must clear the icon. Normalize whitespace immediately, lowercase email, keep the caret stable, and disable autocorrect and capitalization. Keep failed email sign-ins generic so the UI cannot reveal registered addresses.
- Show the «یا ادامه با» divider and alternate sign-in methods only on the initial identity step. Restore them when the user goes back to that step. Keep signup, recovery, and phone entry in the unified card. Route fixed lines to call instructions from the primary action. For numbering plans that cannot distinguish fixed lines from mobiles, offer SMS and call choices beside the identity field. Use the same code editor for SMS and email. Place the exit link below the card with a transparent background. Use «صفحه اصلی» by default and a back arrow and destination label for a valid return URL.
- Keep the identity field LTR when empty, for Latin usernames, for email and for phone. Switch to RTL when a username starts with an RTL letter. Check a complete email domain while typing and on blur, show the result by the field, and keep feedback independent of account existence.
- When the country prefix is +98, remove the domestic zero as soon as the next digit makes it clear that the user is dialing a local number (for example, `09` becomes `9`). Preserve `00` for international entry. Test by typing an incomplete number, as well as pasting a complete one.
- Keep the identity action disabled until the current input is valid. For email, require a successful domain check and give users a retry if the service is unavailable. Color checking blue, success green, invalid input red, and temporary failures amber.
- Name the primary action after the next step. Use «ادامه» for both username and email sign-in because the next screen offers password entry and recovery. Use «ارسال کد پیامکی» for confirmed mobiles, «ادامه با پیامک» when SMS is selected for an ambiguous phone number, «ادامه با تماس تلفنی» for opening call instructions, and «ارسال کد به ایمیل» on the passwordless email path. Once a code field is shown, use «تأیید کد».
- On the password step, keep «ورود» and «بازگشت» directly below the password input, followed by the recovery caption and «ورود بدون رمز عبور». Show the assigned office extension below the passwordless action when the trusted workstation identity matches. Show a real profile photo only for the account assigned to the trusted request IP.
- Keep controls stationary on hover. Use color, border, underline or shadow to show hover without translating the control upward.
- Give disclosures and controls revealed by input a short transition that explains the layout change. Animate the space the content occupies and use a light fade. Keep the focused control usable, avoid replaying motion on every keystroke, and show the final state immediately for reduced motion. Verify opening and closing in the rendered interface.
- Center the SVG and text together on SMS and passkey buttons with the shared 10 px gap. Place «رمز خود را فراموش کرده اید؟» on a separate, noninteractive line above the passwordless button, aligned to the start of the form. Give the caption room above it, use the main text color, and leave its icon off. Keep password input LTR in both visibility states, and center the eye icon vertically using the accent color. Run the browser spacing check for both Digits and username/email password steps and the passkey action before shipping.
- Keep sign-in step transitions within the form. Fade the incoming content without sliding the card, delaying focus, or animating the hero. Keep back navigation and reduced motion immediate and usable.
- Use the shared Digitalogic password field and reveal button throughout the login and recovery pages, including Digits steps loaded after the page opens. Preserve each provider input and its validation rules. Share checks that enforce the same rule and keep sign-in requirements separate from new-password policy.

- Keep the current Digits challenge, Remember me choice and return destination through a retry or refresh in the same tab. Restore the OTP step without sending a code again or storing the entered OTP, password or CAPTCHA response. If a verification response is interrupted, confirm completion against the existing authenticated WordPress session and the same attempt before advising the user. Keep genuine denials intact and guide the user from the current form.

## Digitalogic interface design

Before implementing or reviewing any user-facing interface, read and follow [Contextual UI and no narration](docs/CONTEXTUAL-UI.md). This standing ecosystem contract covers state-driven rendering, progressive disclosure, semantic actions, conditional affordances and stable layout. Apply it across related controls, preserving existing safety and authorization requirements.
